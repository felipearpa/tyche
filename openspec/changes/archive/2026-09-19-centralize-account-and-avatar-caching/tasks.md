## 4. Cross-platform rollout and verification

- [x] 4.1 Verify upgrade behavior on both platforms using account data persisted by the previous release, confirming the gambler stays signed in and sees the same account before reconciliation
  - iOS verified on a device (legacy 150-byte blob → envelope, authenticated refresh, session kept). Android verified on an emulator, because the owner's phone had already migrated and 1.7.2 cannot read the new format (judging by its code, it would throw at startup): `android/1.7.2` built from the tag, signed in by the owner, upgraded in place — still signed in with the same account, authenticated `GET /accounts/me`, and the stored entry grew from 150 to 201 bytes of plaintext, exactly the envelope.
- [x] 4.2 Verify on devices that a username changed by another client reconciles after an eligible trigger, refresh failure preserves cached content, and late refresh or mutation results cannot restore stale or logged-out state
  - Reconciliation, fresh suppression, stale triggers, offline failure and recovery were observed on an Android phone and an iPhone. Result ordering and logout races cannot be staged by hand; they rest on the coordinator tests (2.7, 3.7).
- [x] 4.3 Verify on devices that fresh avatars move among Profile, drawers, toolbars, username preview, and leaderboard without URL access; unchanged stale entries use conditional revalidation; changed remote photos replace active consumers; and offline revalidation retains the stale image
  - Android verified in full on a phone. iOS verified on a simulator (the phone cannot be tapped from a terminal): fresh reuse across every surface with no avatar request, a `304` for an unchanged stale entry, and a replaced remote photo reaching all active consumers through both store paths with no fallback flash; the phone adds the no-re-download evidence. Offline retention was not observed on screen on iOS — a simulator shares the Mac's network — and the owner accepted the store test `offlineRevalidationRetainsStaleImage` for that clause (re-run 2026-09-19, passing).
- [x] 4.4 Verify a successful local avatar upload updates every visible compatible surface from memory without an avatar GET, while a failed upload preserves the previous shared image or fallback
  - Successful upload observed on an Android phone and an iOS simulator (verification.md, 2026-09-19): presign + PUT only, active consumers updated from memory, no avatar GET. On Android a size never requested before transferred the uploaded photo once afterwards, which the spec allows, without re-keying. The failed-upload half was not staged on a device; the owner accepted the upload use-case and Profile view-model tests for it.
- [x] 4.5 Deploy and smoke-test `GET /accounts/me` before mobile release, then run strict OpenSpec validation and record the final backend, iOS, and Android test commands/results in this change
