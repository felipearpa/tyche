## 4. Plural agreement (both platforms)

- [x] 4.0a iOS: gave `leaderboard_points_accessibility`, `leaderboard_movement_up_accessibility`, `leaderboard_movement_down_accessibility`, and `gamblers_text` `variations.plural` `one`/`other` forms in all three locales; left `leaderboard_rank_accessibility` flat (a position, not a quantity) and `points_text` flat (an abbreviation). A repo-wide sweep of every string table on both platforms found one further flat counted noun outside the pool module — `suffix_point_text`, the pool-home drawer's score suffix, one tap from the rows this change fixed — so it was pluralized too, on both platforms. Deleted `LocalizedFormat.swift` and moved every call site in `GamblerScoreItem.swift` and `PoolScoreItem.swift` onto the generated string symbols, which carry the count so the catalog can select a category — the helper resolved the key before applying the format and would have returned the raw `%#@…@` token. Verified: `xcodebuild build -scheme Pool` succeeds and no raw `localized: "…"` literal or `localizedFormat` call remains in `iOS/Pool/Sources/`.
- [x] 4.0b Android: converted the same four keys from `<string>` to `<plurals>` with `one`/`other` items in `values/`, `values-es/`, and `values-es-rES/`, and moved the call sites in `PoolScoreItem.kt` and `GamblerScoreItem.kt` to `pluralStringResource(id, count, count)`. `R.string` → `R.plurals` is a different namespace, so the compiler enforced completeness. Verified: `:pool:compileDebugKotlin` succeeds.
- [x] 4.0c Added singular / plural / zero boundary cases to both platforms' row tests (`1 point, 1 member, Up 1 place` — `2 points, 2 members, Up 2 places` — `0 points, 0 members`) and re-baselined every existing assertion that had encoded the ungrammatical form. Verified: iOS 15/15 and Android 22/22 pass. The re-baselined assertion in `GamblerScoreItemRankPreviewTests` is **not** among them — that class cannot run on local Xcode (see 2.6) — so `GamblerScoreItemAccessibilityTests` was added as a ViewInspector-free exact-match guard on the same composed label, and it does run. Both platforms' substring probes were also converted to exact matches: "Up 1 place" is a prefix of the ungrammatical "Up 1 places" they were written to catch, so as substrings they had stopped discriminating between fixed and broken output.
- [x] 4.0d Recorded the visible consequences. Two visible strings change, both only at `n = 1`: the pool row's member count reads "1 member" and the pool-home drawer's score suffix reads "1 point". The delta spec's visible-design requirement was amended to permit exactly these and nothing else. **Not observed:** either string rendered at `n = 1` in the running apps.
- [x] 4.0e Also pluralized `suffix_point_text` in the app module on both platforms — `iOS/Tyche/Tyche/Localizable/Localizable.xcstrings` (its call site needed no edit, the generated symbol already carries the count) and all three `Android/app/src/main/res/values*/strings.xml` with `DrawerView.kt` moving to `pluralStringResource`. Without it a one-point gambler would have seen "1 member" on the list and "1 points" in the drawer opened from it, while both CHANGELOGs already promise counts read correctly at one. Verified: `:app:assembleProdDebug` and `:app:testProdDebugUnitTest` pass. **Not covered by a test** — the drawer has no announcement or rendering assertion on either platform.

- [x] 4.0f Gave every Spanish plural its CLDR `many` category on both platforms — 10 Android `<item quantity="many">` entries across four `values-es*` tables and 10 iOS `many` variations across the two string catalogs — with the same text as `other`, since these format as plain integers. Verified: `:pool:lintDebug` and `:app:lintProdDebug` now report 0 `MissingQuantity` (down from 8 and 2), and iOS 15/15 plus Android 22/22 still pass. English keeps `one`/`other`, which is its complete rule set.

## 5. Cross-platform verification

- [x] 5.1 Visible design confirmed unchanged **by diff and by test**, not at runtime: no layout, spacing, color, typography, or visible-copy line changed on either platform — the diffs add only semantics modifiers, the `onOpen`/`placeholderModifier` parameters, and the description builders. Both wrappers keep their original tap/click gesture and padding, so row tap still opens the pool and the invite control still starts the invite flow; `PoolScoreListAccessibilityTest` fires both callbacks and asserts the pool id reaching them. **Not observed:** the empty state, error state, and placeholder lists compared side by side in the running apps. Two visible strings change by design, both only at `n = 1` — see 4.0d.
- [x] 5.2 Announcement **order** matches across platforms (pool name, rank, points, members, movement) and neither platform reads the abbreviated "pts." text — both asserted by the per-platform tests. Announcement **wording now matches too**: the divergent leaderboard strings were reconciled to the canonical table in design D5a — six iOS entries changed value, one Android entry changed value, and iOS's two `..._missing_...` keys were renamed to Android's spelling. Verified: the iOS and Android test suites now assert byte-identical English announcement strings for the same model, the iOS rename was checked by a repo-wide grep for the old key names returning zero hits, and all 15 iOS + 22 Android tests pass. **Not verified:** the Spanish cells, which carry no test coverage on either platform — see 5.3.
- [x] 5.3 **Verified on a signed-in iPhone 18 Pro simulator.** Visible copy in `es-CO`: the title reads "Mis pollas" (Colombian register), and the three real pools read "13 jugadores", "1 jugador" and "3 jugadores" — singular and plural both correct. Announcements captured by running `PoolScoreItemAccessibilityTests` under `-testLanguage es -testRegion CO`, which produced the real composed labels: "Puesto 3, 1 punto, 1 jugador, Subió 1 puesto", "Puesto 3, 2 puntos, 2 jugadores, Subió 2 puestos", "Puesto 3, 0 puntos, 0 jugadores, Puesto sin cambios", and "Puesto no disponible, Puntos no disponibles, 101 jugadores" — every aligned phrase and every plural boundary correct in Spanish. **One gap:** the label was read from the composed property, not from the live accessibility tree — this session's simulator `inspect` action was unavailable — so nobody has heard VoiceOver speak it. The composed string is what `.accessibilityLabel` receives, so the remaining risk is in VoiceOver's delivery, not the text.

- [x] 5.4 **Checked on device, found broken, fixed, re-checked.** At `accessibility-extra-extra-extra-large` on the iPhone 18 Pro the row originally failed the spec's legibility requirement three ways: "13 members" wrapped mid-word into "me / mbe / rs", the rank tile clipped its digit, and the pool name broke mid-word ("Mund / ial"). Android at its maximum 2x font scale wrapped text correctly but clipped two-digit ranks — **rank 13 drew as "1"**, losing a digit of real data.

  Fixes, verified by pixels on both platforms:
  - iOS `PositionIndicator`: the digit is now `lineLimit(1)` + `minimumScaleFactor`, so it can never be cut off by the tile's `clipShape` at any size. Benefits the leaderboard rail too, which has the same fixed-size tile.
  - iOS `PoolScoreItem`: the rank tile and invite icon scale with Dynamic Type (`@ScaledMetric`), and at accessibility sizes the row reflows from three columns to full-width rows — three columns cannot share 400 points, which is what forced the mid-word breaks. Word wrapping is restored and "13 members" is complete.
  - Android `PositionIndicator`: the digit auto-sizes (`BasicText` + `TextAutoSize.StepBased`, `maxLines = 1`), so "13" stays whole. Android's text wrapping needed no change — checked before changing anything.

  Re-verified at `accessibility-extra-extra-extra-large` on iOS (name wraps on word boundaries, "13 members" complete, "8" whole, invite operable) and at 2x font scale on Android (two-digit rank complete). Confirmed **no regression at default text size** — the row is pixel-identical to before, still one line per row with "1 member" singular. iOS 15/15 and Android 22/22 pass.

  **Verification was pixel-based and one-off**, via a throwaway instrumented screenshot capture on Android that was deleted afterwards. Neither platform has an automated guard against this returning: a semantic assertion cannot see clipping, since the text node reported "13" even while only "1" was drawn. A screenshot-comparison test would be the durable guard and is not in this change.
